# Command Direction Analysis - NASCAR.ELF

## Overview

Commands in the NASCAR protocol have specific directions. Some are bidirectional, some are server-only, and some are client-only (outbound).

## Key Observations

### Client-Only Commands (No Handlers)

These commands are **generated by the PS2 client** and sent to the server. The binary does not contain handlers for them because:
- They are outbound messages
- The server processes them
- The client just builds and sends them

**Network Commands (ProtoAries Layer)**:
- All use the ProtoAriesSend() function
- No dispatch handlers in the binary
- Server must implement these handlers

**LobbyApi Commands**:
- `move` - Client sends to join rooms
- `addr` - Client sends in response to @dir

### Server-Only Commands

These are **generated by the server** and sent to the client:

- All `+` prefix commands (+ses, +msg, +who, +rom, +pop, +usr, +rnk, +snp)
- `@dir` - Redirect command

### Bidirectional Commands

These commands can be sent by either side:

- LobbyApi: auth, acct, skey, Sele, snap, pers, ping, room, chal, auxi, peek
- BuddyApi: All commands

## Handler Distribution

| Category | Has Handler | Outbound Only |
|----------|-------------|---------------|
| LobbyApi (22) | 22 | 2 (move, addr) |
| BuddyApi (11) | 11 | 0 |
| Network (12) | **0** | 12 |

**Important**: All Network/ProtoAries commands are outbound-only from the client perspective. The server must implement handlers for all of them.

## Implementation Notes

When implementing a server emulator:

1. **LobbyApi handlers** - Implement all 22 LobbyApi commands
2. **BuddyApi handlers** - Implement all 11 BuddyApi commands  
3. **Network handlers** - Implement all 12 Network commands (PING, AUTH, RECV, SEND, ADMN, PGET, RGET, ROST, RADD, RDEL, dper, cper)
